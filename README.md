# 未送达 · UNDELIVERED

**让没有发出求助的地方，也进入通信保障的决策视野。**

面向乡镇应急通信演练的协同工作台：发现信息空白，核实未知状态，比较资源方案，并追踪消息从发送、终端接收到人员确认的全过程。参赛方向为华为云 AgentArts 的 Agent 设计和应用，侧重创新探索。

**当前版本：v0.2，本地可运行原型。** React + TypeScript / FastAPI / SQLite，普通 CPU 可运行。四个角色目前采用确定性规则；华为平台、多模态模型、向量 RAG 和 LoRA 是后续建设任务。当前工程验证为 **30 项后端测试 + 18 项界面交互测试通过**，不是模型成绩或真实救灾效果。

[故事与应用价值](docs/story-and-value.md) · [三分钟演示脚本](docs/demo-script.md) · [架构与实现边界](docs/architecture.md) · [后续任务](docs/backlog.md) · [GitHub Issues](https://github.com/carefree1206/HW_Agent/issues)

## 从一张安静的地图开始

凌晨，暴雨仍在继续。指挥台不断收到城区告警，两支保障队伍和一套便携通信设备等待分配。地图边缘的鹿鸣村没有求助记录。

它真的不需要帮助吗？

鹿鸣村最后一次心跳早已停止更新。系统把它标记为“未知”，用有限的核实预算查询监测节点，确认通信中断。随后，规划器计算两组队伍分配，检查道路、设备和电量，提出待审方案。

就在准备执行时，通往鹿鸣村的一段道路被关闭。原方案和原批准失效，新方案必须重新审查。链路在演练中恢复后，工作台仍等待另一件事：那条消息，是否真的抵达终端，是否有人明确确认看见。

这是一个虚构演练故事，背后的问题是真实的：**依赖上报的系统，怎样处理那些已经无法上报的地方？** [ITU 应急通信工作](https://www.itu.int/itu-d/sites/emergency-telecommunications/)说明了灾前预警、灾后信息流通与连接恢复的重要性。本项目把其中的信息缺失与送达核验问题，转化为可操作、可复盘的演练任务。

## 谁会使用，解决什么问题

| 首批目标用户 | 现有工作中的难点 | 本作品的切入点 | 试用需要验证的价值 |
| --- | --- | --- | --- |
| 通信专业实验室、课程教师 | 预案、算法和终端实验分散 | 一套可重复的故障、核实、规划、回执演练 | 准备工时、复现实验成功率、学员判断准确性 |
| 校园或园区演练组织者 | 容易把“消息发出”当成“通知完成” | 分别记录发送、终端接收和人员确认 | 未确认目标发现时间、补发成功率 |
| 运营商或集成商培训团队 | 情报不完整、资源不足、条件不断变化 | 候选方案比较、旧批准失效、失败原因和复盘 | 不可执行方案率、检查成本、人工审查时间 |

以上为拟验证的应用价值。目前没有真实运营商部署、用户节省工时或人员安全成效数据；首个落地点是教学与培训演练。

## 创新主张及证据

| 设计主张 | v0.2 已能展示 | 比赛版还需证明 |
| --- | --- | --- |
| 让信息缺失成为显式待办 | 未知状态与离线状态分开；核实消耗预算并生成证据 | 主动核实能否在同预算下减少漏判、改变更有价值的行动 |
| 解释“为何这样分配” | 有限分配枚举 + Dijkstra、两组候选、六类独立约束检查、不可行缺口 | 扩大场景、引入时间窗等约束，与相同工具预算的基线比较 |
| 将建议与实际结果逐段核对 | 批准绑定快照和摘要；旧方案不能执行；通知回执按批次独立统计 | 真实 AgentArts Trace 与业务事件贯通，弱网与工具失败下保持一致 |
| 保留不知道的内容 | 上传原始素材、版本化规则来源、待核实字段 | 模态融合、RAG 和 LoRA 是否降低未知项误填、过期引用与冲突误判 |

这是一组应用设计和待验证的技术假设。当前不宣称世界首创，不将 MCP、RAG、多智能体或 LoRA 本身作为原创算法。[技术论证与验证方法](docs/story-and-value.md)给出更完整的说明。

## 当前可以做什么

| 能力 | 实际状态 |
| --- | --- |
| 界面 | 指挥中心、现场报告、方案与资源、回执中心、运行记录；地图选择、缩放、手机区域选择 |
| 角色协作 | 态势、核实、调度、核验四个确定性本地角色；尚无大模型推理 |
| MCP | 3 个本地 HTTP JSON-RPC 服务，12 个工具；初始化、发现、参数检查、完整响应持久化 |
| 调度 | 有限队伍分配枚举 + Dijkstra；候选比较、选择理由、失败诊断、独立校验 |
| 批准与执行 | 批准绑定演练、快照、约束和内容摘要；参数绑定幂等键；新方案替代旧草案与批准 |
| 通知与终端 | 实际软件消息、分层回执、离线待发队列、迟到响应隔离、当前批次统计 |
| 复盘 | SQLite 事务保存；重置前归档；历史只读查看与 JSON 导出；完整工具响应可读回 |
| 知识 | 8 条项目自定义规则；中文双字切分 + SQLite FTS5 BM25；来源、版本与内容摘要可查 |
| 多模态 | 图片/音频校验、保存和 SHA-256；尚无自动视觉理解或 ASR |
| 华为云与训练 | AgentArts / MaaS / SIS 尚未接入；向量 RAG、LoRA 尚未实现 |

地名、人口、道路和监测响应均为合成素材。资源投放、链路恢复和时间推进是离散图模型仿真；实际回执由浏览器 HTTP 请求产生。人员确认仅表示操作者看见测试消息。R10 拥塞继续跟踪，移动电源仍是未纳入调度的预留资源。

## 获取与运行

建议使用 Python 3.12、Node.js 24，并确认 Python SQLite 支持 FTS5。首次安装不需要云账号或 GPU。

```text
git clone https://github.com/carefree1206/HW_Agent.git
cd HW_Agent
```

Windows PowerShell：

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-lock.txt
npm ci
npm run build
.\start-demo.ps1
```

Linux / macOS：

```bash
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements-lock.txt
npm ci
npm run build
.venv/bin/python -m uvicorn backend.main:app --host 127.0.0.1 --port 8000 --no-access-log
```

打开 **http://127.0.0.1:8000**；接口文档位于 `/docs`。本机 v0.2 已在 Windows 验证，其他系统需以实际安装与测试结果为准。GitHub 仓库上传不等于线上应用部署。

PowerShell 脚本执行受限时，可直接运行：

```powershell
.\.venv\Scripts\python.exe -m uvicorn backend.main:app --host 127.0.0.1 --port 8000 --no-access-log
```

`start-demo.ps1 -Port 8080` 会自动配置内部 MCP 地址。手动改端口时，同时设置 `UNDELIVERED_INTERNAL_URL`，例如 `http://127.0.0.1:8080`。配置项见 [.env.example](.env.example)，该文件是变量说明，不会被应用自动加载。演练数据首次启动时生成，无需复制开发者的数据库。

## 三分钟体验

1. 在初始场景点击“开始协同研判”：鹿鸣村从未知变为经合成监测核实的中断，核实预算从 2 变为 1。
2. 在“方案与资源”查看两组候选：最长预计恢复 44 / 53 演练分钟，总行程 57 / 75 分钟；当前选择 44 分钟方案。
3. 点击“中断关键路段”：RD14 关闭，旧方案失效；重新规划后鹿鸣村绕行，最长预计恢复 51 分钟。
4. 审查、批准并执行演练：链路恢复为仿真，12 条测试消息进入软件流程，终端接收和人员确认仍为 0。
5. 在“回执中心”选择鹿鸣村，接收消息，再点击“我已收到”。两个回执指标分别推进，其他未确认目标仍保留。
6. 可继续体验离线确认与恢复补发；或重置后降低设备电量至 15 分钟，观察不可行诊断：一种最省电的可达分配至少需要 64 分钟，缺口 49 分钟。

重置会先确认并归档，不会覆盖历史演练。完整串词、操作分支、失败兜底和答辩问答见[演示脚本](docs/demo-script.md)。

## 架构与下一步

当前主链路为“前端 → FastAPI → 四角色本地流程 → HTTP MCP → 求解/状态/回执 → SQLite → 前端”。AgentArts 目标架构将用平台应用和子工作流承接角色推理，业务版本、审批和独立校验继续由后端负责。

下一批任务按以下顺序推进，验收条件见[任务清单](docs/backlog.md)：

1. **P0：真实平台链路**——业务 API → 已发布 AgentArts 工作流 → 自研 MCP → 真实返回 → 平台 Trace。
2. **P1：多模态与证据**——语音转写、视觉解析、时空来源对齐、人工更正与未知项保留。
3. **P1：RAG 与多角色**——正式授权语料、混合检索、引用核对、四角色契约及异常分支。
4. **P1：算法与独立评测**——核实决策价值、动态约束调度、同预算对照与失败分析。
5. **P2：领域 LoRA**——分组划分数据，落实加速资源，同基座比较提示词与微调。
6. **P1：试用与答辩交付**——专业规则审查、脱敏试用、真实结果、演示视频与分享材料。

## 开发与验证

后端启动后运行 `npm run dev`，访问 http://127.0.0.1:5173。前端开发服务会代理 API、MCP 和上传文件请求。

```powershell
npm run build
npm run test:web
.\.venv\Scripts\python.exe -m pytest tests -q --basetemp .cache/pytest-local
```

后端测试使用独立进程、端口与 SQLite；界面测试使用 jsdom / React Testing Library，覆盖切页、离线、迟到响应、存储失败和重试。测试通过不等于浏览器视觉验收或平台兼容认证。[v0.2 验证摘要](docs/verification-v02.md)与[迭代记录](docs/iteration-v02.md)可供核对。

默认服务只监听本机，一个实例维护一个活跃演练。远程团队演示前需完成访问控制、HTTPS 和部署验收；目前不是生产应急指挥系统。具体约束见[架构说明](docs/architecture.md)。
