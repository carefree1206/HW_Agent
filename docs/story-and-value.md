# 未送达：故事、应用价值与创新论证

日期：2026-10-22。本文用于团队统一产品叙事、比赛介绍与试用交流。鹿鸣村、人物和事件均为虚构演练素材；故事中的技术节点应能由界面和真实记录支持。

## 一句话介绍

《未送达》是一套面向应急通信演练的协同工作台，帮助操作者发现无法上报的区域，用有限资源核实并安排通信保障，最终逐项确认消息是否抵达。

## 故事正文

凌晨，云溪县的雨还没有停。

指挥中心的地图不断亮起告警。城区拥塞，溪口村链路中断，新的报告一条接着一条。两支保障队伍、一套便携通信设备摆在资源栏里，调度员必须尽快作出选择。

鹿鸣村在地图最边缘。它没有新的告警，也没有发来求助。

如果调度只从收到的报告开始，这个村庄很容易被略过。但“没有报告”有两种可能：一切正常，或者已经失去发出报告的能力。屏幕上相同的空白，背后可能是完全不同的处境。

《未送达》首先保留这个区别。鹿鸣村被标记为未知，而不是正常。系统找到停止更新的心跳记录，发起一次有预算的核实。合成监测节点返回：链路中断，备用电量仅剩 35 演练分钟。

系统此时还不能宣布问题解决。队伍从哪里出发，便携设备在哪里领取，道路是否开放，运输和部署需要多少电量，每一项都影响能否执行。

规划器列出两组可行分配。一组让最晚恢复时间达到 44 分钟，另一组需要 53 分钟。调度员可以看到路径、设备预留余量和选择依据，再决定是否批准。

准备出发时，南湾村通往鹿鸣村的路段被关闭。画在地图上的那条路线随即失效，先前的批准也不能继续使用。系统重新计算，绕经白鹭镇和东桥村，预计时间变成 51 分钟。变化带来代价，屏幕把代价如实呈现出来。

如果设备电量只剩 15 分钟，系统会停下来，说明至少需要多少、还缺多少。无法完成的任务必须留下原因，等待补充资源或人工改变范围。

演练中的链路终于恢复，一条测试消息被发出。指挥台没有立刻将任务划为完成。消息可能仍在队列里，可能只到达软件终端，也可能尚未被人看到。

操作者打开鹿鸣村终端，接收消息。接收计数变为一；点击“我已收到”，人员确认计数才变为一。此时其他目标的空白仍在，拥塞区域也仍需观察。

故事到这里不以“所有人安全”收尾。我们得到的是一条范围明确的证据：这条演练消息，已经被这个终端收到，并由操作者确认看见。

《未送达》想留下的问题是：**当决策越来越依赖数据，我们能否为那些暂时无法产生数据的人，保留一次被主动寻找的机会？**

## 世界上的问题，怎样落到这个作品

[ITU 的应急通信工作](https://www.itu.int/itu-d/sites/emergency-telecommunications/)将信息监测、预警、灾后关键信息流通和连接恢复列为工作内容。这支持本作品的问题背景。具体的鹿鸣村故事不是现实事件改编，项目尚未获得任何运营商现场接口或救灾数据。

从这个背景出发，我们选取三个可以由普通服务器实现并验证的问题：

| 现实工作中的风险 | 软件中怎样表示 | 可观察的操作结果 |
| --- | --- | --- |
| 缺失上报可能被忽略 | 未知状态、最后观测时间、核实预算 | 核实前后证据变化、是否仍有未知目标 |
| 建议在现实约束下不可执行 | 路段、队伍、领取点、电量、批准快照 | 独立校验、失败缺口、条件变化后的重新审查 |
| 信息发出后没有真正到达 | 通知批次、排队、终端接收、人员确认 | 各阶段独立时间和回执、离线补发、未确认清单 |

## 为什么与华为的技术方向契合

这是团队对应用场景的判断，不代表华为提供了合作或背书。通信保障问题需要把网络状态、云端模型、现场工具与终端结果联系起来，适合围绕 AgentArts 编排、MCP 接入、模型服务及业务观测建设完整作品。

[AgentArts 多智能体文档](https://support.huaweicloud.com/lowcode-agentarts/agentarts_05_0106.html)说明了将请求路由到子工作流或子智能体的配置路线。我们计划把态势、核实、调度、核验组织为角色契约，由平台承接推理与路由；资源约束、版本和回执继续由可检查的业务服务负责。账号可用模型、地域、传输方式与 Trace 字段均需 P0 联调确认。

## 哪些值得作为创新主张

### 1. 按决策影响选择核实对象

候选方法：枚举未知项的有限可能结果，估算这些结果会怎样改变可行方案、最坏等待或保障范围，再扣除检查代价，优先检查真正可能改变行动的未知项。保留不确定性，不能让 Agent 读取隐藏真值。

对照“固定规则核实”“按缺失时长核实”“不主动核实”，固定检查预算和初始可见证据。观察未知区域漏判、无效核实次数、不可行计划与确认时长。当前只有按规则核实的基线，尚无该方法的实验优势。

### 2. 将不确定证据与可执行约束联动

候选方法：将证据适用性、版本和已知约束贯穿规划、审批与执行；输入改变时只重算未执行部分，解释新旧方案的差异。当前具备快照失效、候选比较和有限约束校验，滚动调度、时间窗和概率性证据尚待建设。

验证重点是错误是否真的被拦截、代价是否可接受。不能仅展示模型生成的“已检查”文本。

### 3. 把完成定义在独立回执上

从工具建议到计划批准、仿真部署、消息发送、终端接收、人员确认，每个阶段由自己的证据推进。历史确认不能自动完成新通知，重试不能重复执行。当前已有工程实现，下一步需在真实平台和网络故障条件下验证。

这是系统可靠性设计；若要宣称学术新颖性，还需做相近工作检索和正式实验。不能把完整工程组合直接描述为原创算法。

## 应用价值如何形成证据

首轮试用建议找一支能审核规则并组织演练的教学或培训团队。参与人数、工时节省和满意度均待实际采集，不预填有利数字。

试用使用相同难度的 A/B 场景：一组采用原有记录方式，一组使用工作台；交叉安排操作顺序，记录经验、任务完成时间、漏判、错误批准、未确认目标和访谈反馈。测试失败保留；人员确认不当作人员安全指标。

| 价值假设 | 指标与分母 | 需要保留的证据 |
| --- | --- | --- |
| 更早发现信息空白 | 应发现的未知目标中被正确识别的比例；发现耗时 | 独立场景真值、可见输入、操作日志 |
| 减少无效核实 | 无新增决策信息的核实次数 / 总核实次数 | 各动作成本、结果及方案变化 |
| 减少不可执行建议 | 独立校验失败计划 / 全部生成计划 | 计划、约束、校验器版本、失败原因 |
| 更完整地跟踪送达 | 终端接收数或人员确认数 / 当前批次预设目标数 | 原始回执、超时、失败与补发记录 |
| 降低演练组织成本 | 准备和复盘分钟数，配对比较并报告差异 | 任务定义、计时、参与者经验和访谈 |

## 对外表述口径

可说“已完成可运行原型和工程回归”“具备本地 MCP、约束校验和真实软件回执”“面向 AgentArts 建设比赛版”。

尚不能说“已在华为平台运行”“已完成多模态推理/LoRA”“成功救助多少人”“优于现有系统”“世界首创”。未来数字应附版本、数据划分、对照设置和原始记录。参赛目标可以是国一，获奖与效果不能提前写成结果。
