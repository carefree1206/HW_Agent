**《未送达》实施路线 v1.0**

> 历史设计基线：当前已实现能力见 [README](../README.md)，当前待办与验收见[任务清单](backlog.md)。本文件中的技术栈、规模与日期为目标设计，不能据此推断平台或训练已完成。

日期：2026-10-18。当前阶段为实施设计；已核对公开平台文档，账号实际可用服务、资源配额和项目效果均待联调验证。本文中的样本量、资源规格、超时和验收数值是拟定配置或目标，不是已取得的结果。

1. **最终产品：乡镇级应急通信保障演练与辅助决策系统。**

   面向通信保障培训人员、校园应急演练组织者，以及运营商或集成商的应急保障团队。输入现场图像、语音、文字和站点状态，发现未知区域与冲突证据，提出核实任务，生成受资源约束的通信保障方案，并跟踪终端接收及人员确认。

   产品要回答四个问题：哪里没有可靠信息；还应核实什么；有限设备和人员怎样安排；哪些消息已经得到验证。实际效益以漏判、未确认时长、送达率、演练准备与处置工时衡量。

   首版领域固定为暴雨背景下的乡镇通信保障演练。通信设施恢复与人员设备投放采用明确标注的仿真模型；消息发送、断连、缓存、补发及回执采用真实软件流程。无线传播、真实基站控制、现场道路通行和灾害预测属于后续专业合作验证范围。首个合作目标是一支可以组织演练并审查业务规则的校内或行业团队。

4. **主架构与唯一的比赛执行路径。**

   ```mermaid
   flowchart TD
       U["指挥台 / 现场录入 / 演练终端"] --> B["业务 API：鉴权、事件版本、持久化任务"]
       B --> A["AgentArts：主控制器与四个角色工作流"]
       A --> K["AgentArts 两个知识库"]
       A --> O["态势 MCP"]
       A --> P["规划 MCP"]
       A --> D["执行与回执 MCP"]
       O --> M["视觉 API / SIS / 领域抽取模型"]
       O --> S["共享事件库与来源索引"]
       P --> C["主动核实策略 / 约束求解器"]
       D --> N["消息网关 / 终端 / 人员确认"]
       N --> S
       S --> B
       E["隔离的场景注入器与评估器"] --> N
       E --> X["独立真值与评分结果"]
   ```

   前端通过业务 API 创建持久化任务，后台 worker 调用 AgentArts 发布后的应用 API。AgentArts 调用知识库和 MCP，结果回写共享事件库。后台 worker 可以在新情报到达后发起下一轮平台请求。AgentArts 必须参与主路径，不能仅展示一张编排截图。

   场景真值、故障注入控制和评测答案放在隔离的评估端，不作为 Agent 的查询工具。工作流可见的是当轮允许获得的报告和工具结果。

5. **AgentArts 里实际创建的对象及顺序。**

   先验证平台调用，再建设多智能体。按以下顺序创建：

   | 顺序 | 对象名建议 | 内容 | 发布条件 |
   |---|---|---|---|
   | 1 | `wf_ping` | 开始 → MCP 健康查询 → 结束 | 可从业务 API 调用，保存工作流和 Trace ID |
   | 2 | `kb_runbooks` | 演练预案与适用规程 | 10 条检索样例均能追溯原文 |
   | 3 | `kb_devices_cases` | 设备手册与开发期案例 | 设备版本及案例来源可查询 |
   | 4 | `wf_assess` | 感知、证据合并、未知项识别 | 返回合法 Assessment 对象 |
   | 5 | `wf_probe` | 选择核实动作，读取核实结果 | 有预算、超时和待核实分支 |
   | 6 | `wf_plan` | 检索规则、组织约束、求解及校验 | 返回可审查计划或无可行方案说明 |
   | 7 | `wf_verify` | 执行状态、回执检查、结案说明 | 终端回执和人员确认分别记录 |
   | 8 | `wf_bootstrap` / `wf_error` | 载入快照 / 输出结构化异常 | 异常不导致业务状态被误记为完成 |
   | 9 | `undelivered_controller` | 将业务事件路由到四类角色工作流 | 每个角色都能被实际触发和追踪 |

   官方多智能体文档描述的是意图路由和子工作流。首版采用明确的 `action`、`incident_id`、`snapshot_version` 组织调用，先用意图工作流把 action 映射为平台实际生成的 intent ID，不把关键业务顺序完全交给自由提示词。

   工作流 MCP 节点的工具固定，参数可由上游模型或代码节点提供。例如核实 Agent 选择 `probe_type`，再由固定的 `obs_request_probe` 节点调用。若需要动态选择多种工具，必须单独验证对应单智能体或托管执行方式，不能假设工作流节点会自动自主选工具。

   外部通知、审批恢复和长任务状态采用后端持久化事件管理。首版不依赖一个长时间存活的模型会话。

6. **一轮实际业务流程。**

   输入：现场报告、异常状态或指挥员操作。业务 API 创建 episode 和任务，读取当前事件版本。

   第一步，`wf_assess` 通过态势 MCP 读取素材处理结果和站点状态；文本、图片和语音都变成带来源的 Evidence；代码节点检查字段并合并冲突。输出未知区域、冲突项及证据引用。

   第二步，`wf_probe` 判断是否还缺少能改变计划的关键信息；在预设核实预算内选择一次核实动作。若结果尚未返回，任务进入 `awaiting_probe`。后台收到新证据后重新发起平台调用，不能把“提交核实请求”当成“已完成核实”。

   第三步，`wf_plan` 检索适用规程，读取资源与道路状态，生成约束集合，调用规划 MCP。独立校验器检查资源冲突、时效和部署条件。输出带快照版本的计划草案。

   第四步，指挥员在界面审查计划及取舍。批准操作由业务 API 生成绑定计划内容、版本和期限的审批记录。模型不能自行生成有效审批记录。

   第五步，`wf_verify` 通过执行 MCP 下发获准的演练任务，查询终端回执及人员确认。新报告导致快照变化时重新校验未执行动作；过期计划进入 `stale`，重新规划后重新审查。

   第六步，输出可下载的处置记录：用了哪些证据、引用了哪些规程、采用哪个计划、工具实际返回什么、哪些区域仍未确认。失败和未知保留在结果中。

8. **多模态处理做什么，怎样保持可追溯。**

   语音：上传短录音 → 保存 OBS 原件 → SIS 转写 → 保留原始转写和时间片段 → 领域抽取模型输出结构化事实。文本纠错是派生记录，不覆盖原始转写。

   图像：保存原图及上传元数据 → 视觉模型识别可观察内容 → OCR 读取路牌/设备标识等 → 对齐已知实体 → 保存证据位置。图片缺少可信拍摄时间或定位时，该字段为空并触发核实；照片本身只能支持可观察事实，不能自动证明道路当前可通行或设备可安全部署。

   文字：解析事件、地点、时间、实体和否定/不确定表达，保留对应原文区间。相同照片或转发消息通过哈希与来源关系去重，转发数量不等于独立证据数量。

   站点时序：用可配置阈值识别心跳缺失、链路或供电异常，保留原始序列。先记录 `heartbeat_missing`，进一步查询后再确定通信状态。

   统一 Evidence 至少包含：证据 ID、模态、来源、原件引用、发生/接收时间、地点精度、观察到的事实、未知字段、冲突引用、验证状态。首版不把模型自报置信度当成经校准概率。

   结构示例见 `examples/incident.example.json`。

9. **RAG 的具体建设路线。**

   `kb_runbooks` 保存规程、预案、演练负责人确认的保障规则。`kb_devices_cases` 保存设备文档和开发期案例。每份资料登记文档 ID、来源、版本、发布日期、有效期、适用区域/设备及使用权限。演练自定规则显式标为演练规则，不能冒充厂家规格或行业标准。

   文档先按条款、操作步骤和表格语义切片。起步可试 400–800 中文字符的段落块及 80–120 字符重叠，平台实际参数限制与 tokenizer 需要联调后统一冻结。表格保留表头、单位和条件，避免设备时长或功率丢失适用前提。

   检索起步采用关键词与向量混合召回，候选目标 10–20 条，重排后提供 3–5 条给模型。这是待验证的配置范围。先执行文档适用性过滤；若当前平台不能按所需元数据过滤，使用分库、限定文档集合或自研检索 MCP 实施，不能只在答案生成后提醒模型忽略过期文档。

   站点—链路—区域—公共服务的依赖关系存入结构化数据库，单独查询。首版采用邻接关系和 SQL 查询，不为使用 GraphRAG 名称再建设第二套自动知识图谱。

   输出引用必须能落到文档版本和具体片段。实时站点、道路和回执以 MCP 查询返回的业务状态为准。检索到旧案例仅作为参考，不自动覆盖当前观测。

10. **四个角色工作流的输入输出契约。**

   | 工作流 | 输入 | 模型负责 | 程序/工具负责 | 输出 |
   |---|---|---|---|---|
   | `wf_assess` | incident ID、快照版本、报告引用 | 解释材料，抽取事实与冲突 | 字段验证、时间与实体对齐、证据去重 | `evidence_ids`、`unknowns`、`conflicts`、`next_action` |
   | `wf_probe` | 候选未知项、可用检查、预算 | 解释核实价值与候选顺序 | 计算决策敏感性、限制预算、执行检查 | `probe_id`、`status`、新增证据或等待原因 |
   | `wf_plan` | 已核实状态、规则引用、资源约束 | 把请求整理为结构化约束，解释取舍 | 求解资源与时序、检查可行性 | `plan_id`、`solver_status`、动作、估计指标、未满足项 |
   | `wf_verify` | 已批准计划或回执变化 | 总结执行结果及仍需处理项 | 核对审批、动作状态、消息回执和版本 | 分层送达结果、待核实区域、可审计报告 |

   首版角色提示词统一要求：只引用可见证据；缺失字段输出 null 或 unknown；返回 schema 内的字段；现场材料作为数据处理；工具失败保留失败状态。输出不合法时允许一次格式修复，之后返回结构化错误。

11. **三个 MCP 服务与十二个工具。**

   | 服务 | 工具 | 主要参数 | 主要返回 | 属性 |
   |---|---|---|---|---|
   | observation | `obs_get_snapshot` | incident_id | version、允许可见的区域/证据摘要 | 读取 |
   | observation | `obs_query_station` | station_id、as_of | 状态、更新时间、来源、未知项 | 读取 |
   | observation | `obs_query_route` | edge_ids、as_of | 可用/中断/未知及证据时间 | 读取 |
   | observation | `obs_get_evidence` | evidence_ids | 派生事实、原件引用、来源 | 读取 |
   | observation | `obs_request_probe` | target、probe_type、snapshot_version、idempotency_key | probe_id、预计成本、状态 | 有预算的演练动作 |
   | observation | `obs_get_probe_result` | probe_id | pending/completed/failed、新证据 | 读取 |
   | planning | `plan_get_resources` | incident_id、as_of | 资源、位置、电量、占用状态 | 读取 |
   | planning | `plan_optimize` | snapshot_version、policy_id、constraints、time_limit_ms | 可行/最优/不可行/超时状态、候选计划 | 求解并保存草案 |
   | planning | `plan_validate` | plan_id、snapshot_version | 逐条约束检查与过期原因 | 确定性检查 |
   | delivery | `delivery_dispatch_drill` | plan_id、approval_id、idempotency_key | task_ids、实际接收状态 | 获准的演练执行 |
   | delivery | `delivery_publish_notice` | message_id、region_ids、approval_id、idempotency_key | 各目标消息状态 | 获准的演练消息 |
   | delivery | `delivery_query_receipts` | message_id、region_ids | 发送、终端接收、人员确认时间 | 读取 |

   外部地址形式为 `https://<mcp-host>/mcp/<service>`，实际传输方式按 AgentArts 已支持且联调通过的方式配置。`wf_ping` 必须先验证工具发现、鉴权、调用、超时和结果解析。

   所有工具统一返回 `request_id`、`status`、`observed_at`、`snapshot_version`、`data`、`error`。常见业务错误定义为 `STALE_SNAPSHOT`、`BUDGET_EXCEEDED`、`APPROVAL_REQUIRED`、`TOOL_TIMEOUT`、`INVALID_ARGUMENT`，它们是本项目的业务返回约定，不是伪造的 MCP 协议错误码。

   调用 `request_probe` 的重复请求不能重复消耗资源。执行服务只接收数据库中有效的审批记录；计划版本、摘要或执行范围变化需要重新审查。Agent 不获得直接读数据库、执行任意 shell 或读取评估真值的工具。

12. **候选自研机制一：针对决策影响进行主动核实。**

   先把区域状态区分为 normal、abnormal、unknown，把未知项关联到计划中的关键依赖。例如桥梁状态会影响队伍能否到达部署点，电量状态会影响设备能否支持演练时窗。

   第一版采用可实现的启发式：为每个核实动作列出有限的可能结果；在这些结果下重新计算候选计划；用“哪些关键约束或资源安排会改变”衡量决策敏感性，再结合核实耗时和资源成本排序。优先处理足以改变行动且成本合理的未知项。评分参数在开发集选定，不能根据最终测试结果调整。

   该方法不声称获得了真实灾害状态的概率分布。具备足够标注后，再研究经校准的概率模型与期望信息价值。

   对照策略包括不主动核实、随机选择核实项、只按核实成本选择。核实动作预算一致。主要测量未知区域漏判、最终已验证送达率、最长未确认时间和核实成本。

13. **候选自研机制二：带保障底线的滚动资源调度。**

   第一版用 OR-Tools CP-SAT 求解。输入是路线图、资源状态、任务时窗、部署条件和演练负责人制定的 policy。时间单位先统一为整数演练分钟；真实 API/模型时延另以毫秒记录。

   硬约束包括：同一队伍同一时段只执行一个任务；同一设备不能同时分配给两处；任务需要满足可达路径、前序步骤、部署条件及电量约束；未确认的关键条件不能直接当作已满足。可选保障要求如果无法同时满足，要返回不可行或未满足项。

   采用两组明确的 policy 配置分别求解并比较，例如覆盖优先和区域保障优先；输出对应预计覆盖、最长未确认时长和行动成本。有限时间返回 FEASIBLE 时仅称可行方案，不能写成全局最优或完整 Pareto 前沿。

   初始求解时限设为 3 秒，超时返回已有可行解或 UNKNOWN。到达新的有效情报后重新求解未执行动作，已完成动作作为事实固定。设备覆盖采用公开说明的简化图模型，不能把图可达性声称为真实射频覆盖预测。

14. **模型选用、微调和部署的具体路线。**

   用稳定别名管理模型：`planner_text_v1`、`vision_v1`、`extractor_base_v1`、`extractor_lora_v1`、`embedding_v1`、`reranker_v1`。首日记录真实 provider、model ID、地域、能力、参数与计费项，存入模型清单，之后每次评测引用清单哈希。

   文本编排模型要求中文理解、工具参数和结构化输出可靠；视觉模型要求能处理拍摄图片与 OCR 任务；SIS 负责语音转写。首版通过 API 调用，普通服务器不承担大模型权重推理。

   LoRA 首选任务为中文应急文本/ASR 转写的事件抽取，输出地点实体、发生时间、可观察事实、否定项、未知项和证据跨度。可先验证 ModelArts 文档示例涉及的 `qwen3_8b` 是否对当前账号开放训练；如果不可用，再在实际可训练模型中选择同类基座并重新测资源。这里是候选，不是已确认可用的账号资源。

   数据路线、划分和对照详见 `data-and-evaluation-plan.md`。不训练灾害预测、生命价值排序或无线电覆盖模型。把快速变化的事实保留在实时状态与 RAG 中。

   微调作业输出基座版本、适配器、tokenizer、配置、数据清单、训练日志和验证集选点记录。部署到可用加速推理服务，经统一抽取 API 调用，`wf_assess` 保持输入输出契约不变。未落实加速资源时，API 基线仍可推进，微调状态明确标为待实施。

15. **消息送达与弱网设计。**

   消息状态至少为 queued、sent、terminal_received、human_confirmed、expired、failed。终端收到需要终端应用实际返回回执；人员确认需要演练操作者显式操作。回执仅证明相应阶段，不能自动推断对方理解、已转移或已经安全。

   网关使用持久化 outbox，消息携带唯一 ID、演练 ID、目标、正文哈希和有效期。终端缓存已处理 ID，重复发送不重复触发业务动作。离线页面可在 IndexedDB 保存待发送报告和确认，恢复连接后按原始事件时间补发，并保留实际接收时间。

   验证重复消息、乱序回执、网络恢复、过期补发和重复点击。采用容器网络代理或 Linux 网络仿真制造延迟、丢包及中断，同时保留注入配置。指挥中心失去网络时云端 Agent 也不能访问新数据；终端只执行已有缓存与预先配置的流程。

16. **业务后端、存储和 API。**

   建议用 Python FastAPI、Pydantic、SQLAlchemy、PostgreSQL、独立 worker；前端用 React、TypeScript 和 SVG/GeoJSON 场景图。首版以 PostgreSQL 持久化任务表和版本检查管理状态；先不引入 Kubernetes 和额外消息中间件。依赖版本在首次可运行提交中固定并保存 lock 文件。

   | API | 用途 | 成功返回 |
   |---|---|---|
   | `POST /api/drills` | 创建演练 | drill_id |
   | `POST /api/reports` | 保存文字或素材引用 | report_id、evidence_job_id |
   | `POST /api/incidents/{id}/assess` | 发起平台态势分析 | job_id，HTTP 202 |
   | `POST /api/incidents/{id}/probe` | 发起核实流程 | job_id |
   | `POST /api/incidents/{id}/plans` | 发起规划 | job_id |
   | `POST /api/plans/{id}/approve` | 人工审批 | approval_id、plan_hash |
   | `POST /api/plans/{id}/execute` | 执行获准演练计划 | job_id |
   | `POST /api/receipts` | 终端回执或人员确认 | receipt_id |
   | `GET /api/incidents/{id}/snapshot` | 获取可见业务状态 | version、状态摘要 |
   | `GET /api/jobs/{id}` | 查询长任务 | status、结果或错误 |
   | `GET /api/drills/{id}/events` | SSE 事件流 | 可续传的事件序号 |
   | `GET /api/drills/{id}/report` | 下载处置记录 | Markdown/JSON 文件 |

   后端不得把 API 密钥返回前端。模型、SIS 和 OBS 凭据配置在服务端环境或对应云身份中，仓库仅提交变量名示例。OBS 原件以 evidence ID 关联，前端经授权查看所需文件。

17. **数据库中的最小核心对象。**

   | 表/对象 | 关键字段 | 需要保证的关系 |
   |---|---|---|
   | drills | id、scenario_version、policy_version、mode | mode 固定标识演练 |
   | regions/stations/road_edges | id、位置/邻接、更新时间、状态 | 图拓扑可版本化 |
   | resources | id、类型、位置、电量、占用、version | 资源占用唯一性 |
   | reports | id、来源、素材引用、报告时间、接收时间 | 原始报告不被派生结果覆盖 |
   | evidence | id、report_id、事件字段、未知项、原文/图像跨度、验证状态 | 可追溯到素材 |
   | incidents | id、drill_id、snapshot_version、status | 事件快照单调递增 |
   | probes | id、目标、动作、预算、状态、idempotency_key | 相同幂等键只执行一次 |
   | plans | id、snapshot_version、policy_version、solver_status、plan_hash | 明确计划所依据的状态 |
   | approvals | id、plan_id、plan_hash、审批人、expiry | 不能批准不同内容的计划 |
   | tasks | id、plan_id、资源、前序任务、状态 | 执行顺序和资源约束 |
   | messages/receipts | message_id、终端、阶段、发生/接收时间 | 消息和回执可去重 |
   | jobs | id、类型、状态、重试次数、request_id | 长任务可恢复 |
   | run_manifests | 代码、配置、模型、知识库、数据版本和哈希 | 每次结果可追踪 |

   评测真值使用独立存储/权限边界。开发目录里也不能把完整真值作为任意文件检索工具提供给 Agent。

18. **部署拓扑和成本控制。**

   起步可试一台 8 vCPU / 16 GB 级别的普通 Linux ECS，部署网关、业务 API、worker、PostgreSQL、三个 MCP 服务和轻量消息终端。这是待压测的资源起点，不是容量保证。AgentArts、模型 API、SIS、知识库和 OBS 使用对应云服务。大规模压测、网络注入和数据库资源干扰明显时，再把仿真端独立到第二台服务器。

   外部可访问的 MCP 地址需要通过平台的网络与鉴权联调；能使用私网接入时先验证相应网络配置。对外入口使用 HTTPS。仅开放联调所需的网关入口，数据库和评测真值不对外暴露。

   第一次试运行记录 ECS 时长、模型输入输出 token、图片调用量、SIS 音频时长、知识库容量/检索、OBS 和训练资源时长。用账号实际单价计算预计成本，分别设置开发、盲测和训练预算。不能把截图里列出的代金券视为已经到账或覆盖所有服务。

   初始运行上限：查询工具 10 秒、视觉/语音任务 60 秒、求解 3 秒、单次模型格式修复 1 次、核实每轮最多 2 次、每 episode 最多 3 轮。首周测得实际延迟后，统一冻结对照方法的预算和超时，不能只为主方法放宽限制。

22. **拟定验收目标与停止扩展条件。**

   12 个冒烟案例必须覆盖正常、报告缺失、图片时间不明、矛盾报告、道路中断、设备电量不足、工具超时、无可行计划、过期审批、重复执行、终端离线、只有终端回执没有人员确认。每个案例定义输入、允许可见证据、预期业务状态和实际结果。

   工程门槛：示例 schema 校验通过；重复执行不产生重复任务；不合法/过期审批不能执行；消息各阶段有实际对应事件；AgentArts 运行可以关联到业务 episode；无可行方案时保留失败结果。

   模型与业务质量的拟定目标：结构化输出合法率至少 98%；独立抽取测试集字段 macro-F1 目标 0.85；引用支持性目标 90%；对需保留未知的字段，误填率目标不高于 3%。这些目标需通过基线试验检查可行性，任何达成声明都要引用实际结果。

   研究门槛：主方法相对最强基线，在固定资源/工具/模型预算下，对已验证送达率、最长未确认时长或核实成本产生可重复的改善，同时报告不可执行计划和误判。如果没有改善，明确收窄技术主张，不用增加 Agent 数量掩盖问题。

   独立测试与真值要求详见数据文档。仿真结果、软件网络实验和用户演练反馈分别注明来源；不据此宣称真实灾害救援成效。

   | 3:40–4:30 | 执行获准演练计划，先恢复终端连接，再由另一终端操作者确认 | 任务事件、终端回执、人员确认三层记录 | 以可验证的消息完成故事 |
   | 4:30–5:00 | 显示仍未确认项、运行成本和已完成的独立测试结果 | Trace、结果清单与失败案例链接 | 给出项目能力及真实边界 |

   台词围绕可观察的动作，避免用虚构数字宣称真实救援收益。最后保留“未确认区域”指标，让观众看到系统还需要完成哪些工作。
